# 구현 계획 로드맵

구현을 다섯 개의 계획으로 나눠 실행한다. 각 계획은 **그 자체로 동작하는 결과물**을
내고, 끝나면 계획서를 지우고 이 문서를 갱신한다 — 완료된 계획의 내용은 코드와
git 히스토리, 그리고 스펙에 남는다.

| 계획 | 단계 | 결과물 | 상태 |
|---|---|---|---|

| 2 | 4~8 | 렌더 → 편집 → `sync` → `status`. AI가 코멘트를 처리할 수 있다 | **완료** (2026-10-13, 17 커밋) |

## 계획 3 — 완료

9, 10, 12단계. `push`까지 완결된 CLI. 답글과 resolve가 GitLab에 올라가고, 중간에
죽어도 중복 없이 복구된다. `--draft`/`--publish`로 리뷰 한 라운드를 묶어 보낼 수
있다. 483개 테스트.

구현된 FR: FR-008~FR-011(`push`, 일반 notes 경로 + 멱등성), FR-016(`doctor`),
FR-017(`clean`), FR-019(`open`), FR-013(`--draft`).

설계에서 스펙에 반영된 것 셋 — `server.missing`으로 사라진 스레드를 보존하고
`push`가 제외한다(결정 0011), draft 생성은 전송이 아니므로 `local.reply`와
`pushed_hash`를 발행 시점에만 갱신하고 `bulk_publish`는 확인을 요구한다(결정
0012), `status`의 `push` 블록과 `push`의 사전 판정은 같은 함수를 쓴다
(`spec/cli.md` §8).

### 실측 — 한 바퀴 완료 (2026-10-14)

`gitlab.com/jngbng/mr-helper` MR `!1`(코멘트 15개)을 클론해 `pull` → 처리 →
`sync` → `status` → `dry-run` → `push` 를 끝까지 돌렸다. **성공 기준(코멘트 15개를
30분 내)은 도구 쪽에서 병목이 아니다** — CLI 전체 오버헤드가 21초다.

| 단계 | 측정 |
|---|---|
| `mrq pull` | 3.40초 (스레드 15, 비위치 코멘트 3 제외하고 exact 12 / fuzzy 0 / stale 0) |
| 위치가 틀려서 직접 찾은 코멘트 | 0건 |
| 코멘트 처리 (AI 1차 패스) | 2분 46초 — 코멘트 14건 읽기 + 소스 3파일 확인 + 답글 12건 작성 |
| `mrq sync` | 0.22초 (14 스레드 반영, 답글 12건) |
| `mrq status` | 0.16초 |
| `mrq push --dry-run` | 0.72초 |
| `mrq push` | 16.17초 (답글 12건 + resolve 2건 = 쓰기 14회) |
| `mrq push` 재실행 | 4.05초, "보낼 것이 없습니다" |
| 총 소요 | 3분 07초 (`pull` 시작 → `push` 종료) |
| 가장 시간을 많이 쓴 지점 | `push` 16.17초 — 쓰기 14회가 순차이고 호출당 약 1.2초(`glab` 서브프로세스 + 왕복) |

**중복 전송 0건을 실물로 확인했다.** 같은 상태에서 `push` 를 다시 돌리면 쓰기 요청이
한 건도 나가지 않는다(`pushed_hash` 1차 방어). 서버 쪽도 대조했다 — 비시스템 노트가
16 → 28개로 정확히 12개 늘고, resolve된 스레드가 1 → 3개가 되고, 코드 펜스가 섞인
답글이 그대로 저장됐다.

처리 시간의 성격을 적어 둔다: 위 2분 46초는 **AI 1차 패스**이고, PRD §2 의 30분
예산이 가정하는 "사람이 그 결과를 검토하는 시간" 은 포함되지 않았다. 측정이 답한
것은 "도구가 예산을 먹지 않는다" 이고, 답하지 않은 것은 사람 검토 쪽 분포다.

**행동 가능한 항목 하나.** `push` 가 쓰기를 순차로 보낸다. 코멘트 50개짜리 MR 이면
같은 비율로 약 1분이 되고, 그 시간 동안 사용자는 진행 표시를 못 본다. 비기능
요구(`PRD` §6)가 `pull` 10초만 못박고 `push` 는 비워 뒀으므로 지금 결함은 아니지만,
스레드마다 즉시 flush 하는 구조(`cli.md` §9 4c)와 병렬 전송은 같이 갈 수 없다 —
동시성을 넣으려면 그 MUST 를 먼저 다시 설계해야 한다. 잔여 항목에 적었다.

## 계획 4 전 과제 — 완료

계획 4 를 설계하다 스펙 둘이 모순인 것을 발견해 먼저 해소했다 (브랜치
`jbseo/pre_step4`). `editor.md` §3.4 는 충돌 버퍼에서 스레드마다 방향을 고르라고
하는데, `cli.md` §5 의 `sync` 는 호출당 방향 하나이고 `data-model.md` §5.3 은
충돌이 하나라도 남으면 전부 실패시킨다 — 혼합 해소가 **어떤 순서로도** 불가능했다.

`--prefer` 를 `[ID=]md|json` 스코프 문법으로 바꾸고 `--thread` 를 없앴다. 좁은
스코프가 순서와 무관하게 이긴다. 523개 테스트. `docs/decisions/0013`.

## 계획 4 — 완료

11단계. flymake 백엔드와 `review.md` 목록 버퍼. **소스 ↔ 코멘트 왕복이 닫힌다** —
`M-g n` 으로 코멘트를 돌고, `C-c m r` 로 답글을 쓰고, 저장하면 `sync` 가 돌고,
`file-notify` 가 열린 버퍼의 진단을 갱신한다. 87개 ERT, 적합성 17건.

구현된 FR: FR-014.

일곱 모듈, 의존은 한쪽으로만 흐른다. `mrq-anchor.el`(의존 0, 적합성 테이블의 대상),
`mrq-core.el`(`review.json` 을 읽는 유일한 창구), `mrq-cli.el`(프로세스를 띄우는
유일한 자리), 그리고 UI 넷. `mrq-boundary-test.el` 이 그 경계를 코드 모양으로
고정한다 — 변형 테스트로 실제로 무는 것을 확인했다.

**`testdata/conformance/anchor.json` 17건이 이 계획의 가장 오래 남는 산출물이다.**
계획 5 가 그것을 통과해야 하고, 스펙 문장만으로는 안 잡히는 것들을 못박는다 —
창 크기, 창 경계의 포함 여부, 공백뿐인 앵커의 strip 생략, trailing 공백 흡수,
그리고 **두 단계의 유일성 가드 각각**. 17번째(`exact 가 둘이면 더 가까운 쪽을
고르지 않는다`)는 최종 리뷰가 찾은 것이다 — 그게 없으면 "최근접 선택" 구현이
16건을 전부 통과한다. **못 잡는 하나**("exact 가 둘이면 strip 으로 안 내려간다")는
관측 가능한 효과가 없다는 것도 함께 적었다 (`repo-layout.md` §4.1).

설계에서 스펙에 반영된 것 넷:

- 점을 옮기기 위한 검색은 파싱이 아니다 (`editor.md` §1)
- flymake 는 `review.md`·`mrq list` 와 **같은 집합**을 보여준다 — 서버에서
  resolve 됐고 미전송 작업이 없으면 감춘다 (§3.1, 결정 0001)
- 파일이 아니라 디렉터리에 watch 를 건다 (§3.1) — Emacs 에서는 동등하지만
  VSCode 는 확인이 필요하다
- 충돌 버퍼는 모든 선택을 모아 **한 번의 `sync`** 로 보낸다 (§3.4, 결정 0013)

**실측은 `2026-10-14-plugin-emacs-dogfood.md`.** 배치 ERT 가 구조적으로 답할 수
없는 것만 담겨 있다 — 다른 flymake 백엔드와의 공존, 키 바인딩 충돌, 그리고 위치
없는 경고의 가시성(잠정 결정)을 재평가하는 관찰 항목.

최종 리뷰(독립)가 Critical 2 · Important 9 를 냈고 전부 고쳤다. 가장 값어치 있던
둘은 **`review.md` 가 편집면인데 평문 `g`/`r` 이 명령에 묶여 있던 것**(답글
첫 글자가 `reanchor` 를 돌린다)과 **적합성 테이블이 exact 단계 유일성 가드를
못 묶던 것**이다. 후자는 계획 5 가 그 문장을 믿고 출발할 참이었다.

### 계획 5 를 위한 메모

- `FileSystemWatcher` 가 `os.replace` 교체를 따라가는지 **직접 확인할 것.**
  Emacs 는 파일 watch 도 부모 디렉터리를 보므로 함정이 없었지만 VSCode 는
  같은 보장을 가정할 수 없다 (`editor.md` §3.1)
- 적합성 테이블의 `buffer_set` 은 **치환**이다 (삽입이 아니다). 전부 1-indexed
- `mrq-anchor.el` 과 1:1 로 대응하는 `anchor.ts` 를 만들고 의존을 0 으로 둘 것 —
  그래야 테이블 테스트가 순수 단위 테스트가 된다

## 계획 5 — `plugin_vscode` (13단계)

**결과물:** Diagnostics + CodeLens. 문제 패널과 `F8` 이동.

FR-015. 스펙은 `spec/editor.md` §4.

**계획 4의 적합성 테이블을 통과해야 한다.** 그게 이 계획의 가장 중요한 수락 조건이다.

MVP에서 `@vscode/test-electron` 하네스를 쓰지 않는다. 확장이 얇아 로직(json 읽기,
앵커 검색)이 전부 순수 함수이고 vitest로 덮인다. Diagnostics/CodeLens 배선은 수동
확인으로 둔다.

**잊기 쉬운 것:** CodeLens의 `✓ Resolve` / `💬 Reply`는 `mrq state` / `mrq reply`를
호출한다. md를 파싱하지도, json을 직접 쓰지도 않는다. 그 CLI 명령이 계획 2에
포함된 이유가 바로 이 확장이다.
