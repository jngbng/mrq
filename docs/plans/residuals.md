## 기능 구멍

### 상대가 답글을 달아도 아무 신호가 없다

`pull` 이 `thread.local` 을 통째로 보존하고(`commands/pull.py:41`), `note_count`
는 `push` 의 동시변경 감지에만 쓰인다 — **`pull` 에서는 한 번도 비교하지 않는다.**

그래서 내가 `[~]`(답글만)로 두고 push 한 스레드에 상대가 답글을 달아도
`local.state` 는 `replied` 그대로이고, `review.md` 에도 flymake 에도 "새 것이
왔다"는 표시가 없다. 리뷰 도구로서 아픈 구멍이다.

신호는 이미 있다 — `pull` 이 이전 `note_count` 와 새 값을 비교하면 된다.
정하는 것: 배지(`new`)로 보일지, `local.state` 를 `todo` 로 되돌릴지. 후자는
사용자의 결정을 덮어쓰는 것이라 조심해야 한다.

## `review.md` 문법 — 미결 셋

셋 다 같은 파일을 건드리고 세 구현의 계약(`spec/review-md.md`)이라, **계획 5
전에 한 번에** 결정하는 쪽이 싸다.

### 앵커 주석의 자리

지금은 앵커가 헤더 **위**라, md 로 보면 메타데이터 주석이 **위쪽 아이템의 body**
로 잡혀 섹션 폴딩이 이상해진다.

막는 것: `review-md.md` §2 가 위에 둔 이유는 블록 경계와 reply 의 끝이 **같은
토큰 하나**로 정의되기 때문이다. 아래로 내리면 "끝에서 헤더처럼 보이는 줄을
떼어내는" 보정이 필요하고, 그 보정은 답글이 `## ` 로 끝날 때 깨진다.

**버린 안**: 헤더 줄 끝에 붙이기(`## [ ] a.py:1 — @x <!-- mrq:... -->`). 경계
문제는 풀리지만 `markdown-mode` 가 주석도 하이라이팅해 보기 나쁘다.

남은 길 둘 — 아래로 내리고 파서의 블록 끝 토큰을 바꾸거나, **md 는 그대로 두고
`mrq-mode` 의 outline 설정만 손보거나.** 후자가 훨씬 싸고 VSCode 와 무관하다.
거기부터 보는 것을 권한다.

### 상태가 reply 에서 멀다

체크박스가 블록 **머리**에 있고 답글은 노트·diff 를 지나 한참 아래 `### reply`
라, 답글을 쓰는 동안 상태가 안 보인다. `C-c m t` 는 거기서도 동작한다 — 문제는
**보이지 않는 것**이다.

검토한 선택지 셋: `### reply` 헤더에 상태를 같이 적기(중복이라 어긋날 여지),
상태를 `### reply` 바로 위로 옮기기(헤더 형식과 `compilation-error-regexp-alist`
가 함께 바뀜), md 는 두고 Emacs 헤더라인에 띄우기(문법 불변, VSCode 는 자기
방식대로).

### 위치 없는 경고를 `review.md` 안에 렌더

`editor.md` §3.4 는 위치 없는 경고를 에코 영역과 `*mrq*` 로만 보낸다. 실측에서
**"알아차리기 힘들다"가 확인됐다** — 그 경고가 알리는 것은 "답글을 썼는데 전송되지
않는다"이고, 놓치면 답글이 그대로 남는다.

결론은 났다: `review.md` 안에 렌더한다. 미구현. 렌더러·파서가 함께 움직이고
`v:` 해시에 포함할지를 정해야 한다(포함하면 경고가 바뀔 때마다 거짓 충돌이 난다).

## CLI

### `push` 의 전송 처리량

2026-10-14 실측에서 쓰기 14회에 16.17초 — 호출당 약 1.2초이고 전부 순차다.
코멘트 50개 MR 이면 1분가량이며 그동안 진행 표시가 없다.

지금 결함은 아니다(`PRD` §6 이 `pull` 10초만 못박았다). 손대려면 순서가 있다:
**스레드마다 결과를 즉시 json 에 쓰는 구조(`spec/cli.md` §9 4c MUST)가 병렬
전송과 같이 갈 수 없다.** 동시성은 그 MUST 를 먼저 다시 설계하는 일이고 크래시
복구 보장을 건드린다 — 진행 표시(스레드별 한 줄)부터가 훨씬 싸다.

### 위치 코멘트를 새로 만들 때 (future work)

`mrq` 는 기존 스레드에 답글만 단다. 새 위치 코멘트(`mrq-design.md` §6)를 할 때
아래가 걸린다. 2026-10-13 실측이다.

- `-F "position[new_line]=15"` 식 bracket 키는 JSON 본문에서 중첩으로 가지
  않는다. glab 1.114 는 조용히 무시했고(위치 없는 스레드가 성공 응답과 함께
  만들어진다), 최신 문서는 에러로 거부한다고 적는다. 어느 쪽이든 쓰면 안 된다
- 중첩은 `-F 'position={"position_type":"text","new_line":15}'` 로 보낸다
- `--input` 을 쓴다면 `-H "Content-Type: application/json"` 을 함께 줘야 한다.
  빼면 GitLab 이 `HTTP 415` 를 돌려준다

### 코드 모양

- `anchor.read_lines` 와 `reanchor._read_worktree` 가 같은 CRLF 정규화·분할·끝
  빈 줄 제거 루틴이다. `anchor._HUNK_HEADER` 와 `linemap._HUNK` 는 플래그만 다른
  같은 정규식이고 각자 별도 hunk 파서를 먹인다. 공유 헬퍼로 모으면 드리프트를 막는다
- `anchor._split_hunks` 가 파일 경계를 무시하고 모든 파일 섹션의 hunk 를 한
  리스트로 평탄화한다. `hunk_for` 는 줄 번호만으로 고른다. `-M` 이 rename 을
  놓치면 선택이 우연히만 맞는다. `hunk` 를 그대로 소비하는 소비자가 생기면
  `+++ b/<path>` 섹션에 선택을 묶어야 한다
- 스키마의 `format: "date-time"` 이 파이썬 쪽에서 장식이다. `FormatChecker` 도
  `rfc3339-validator` 도 없어 `"pulled_at": "not-a-date"` 가 통과한다. 세 구현이
  공유하는 계약이라 더 엄격한 리더가 CLI 가 쓴 것을 거부할 수 있다. 포맷을
  단언하든 키워드를 빼든 하나를 골라야 한다
- `gitcmd.run` 이 공개라 래퍼를 거치지 않을 문이 열려 있다. "모든 git 호출이
  이름 붙은 감사 가능한 래퍼"라는 규율이 `reanchor` 가 네트워크를 안 탄다는 것을
  증명하게 해 준 장치다. `_run` + 이름 붙은 래퍼를 고려할 것
- `.gitignore` 가 `cli/uv.lock` 을 제외하는데 `make deps` 는 `uv sync` 다.
  고정되지 않은 락파일은 피할 수 있는 드리프트다
- `Stats.count` 가 검증 없이 `setattr` 을 쓴다. 네 번째 confidence 값이 생기면
  `as_dict` 가 버리는 유령 속성이 조용히 만들어진다 — 거짓말하는 품질 게이트가 된다

### 테스트 스위트 속도

계획 1 종료 시 346개 50초 → 지금 529개. 비용은 함수 스코프 `git_repo` 픽스처
(테스트당 git 서브프로세스 약 6회)가 지배한다. 실제 git 저장소를 쓰는 것은 옳다
(`reanchoring.md` §8 MUST, `.mrq/` 가시성·`git mv`·rename pathspec 결함을 모두
그것이 잡았다) — 바꿀 것은 **매 테스트 새로 만드는 방식**이다. 세션 스코프 템플릿
저장소 + `cp -r`.

### 최종 리뷰가 유보한 것 (계획 4 전 과제)

- `--prefer` 문법 오류가 md 파싱 에러에 가린다. `prefer.parse` 를
  `mdsync.perform` 맨 위로 올리면 사라진다
- `Resolution.__bool__` 이 죽은 코드이고 함정이다 — 누가 `if resolution:` 으로
  바꾸면 빈 `Resolution`(= `push` 경로)이 falsy 라 경고 루프가 통째로 건너뛰어진다
- `test_sync_pick_on_a_non_conflicting_thread_warns` 가 독스트링의 절반
  ("스코프 없는 `--prefer` 는 경고하지 않는다")을 단언하지 않는다.
  `err.count(...) == 1` 로 닫힌다
- `_guard_collision` 메시지가 전역 적용을 원한 사용자에게 출구를 안 준다
  (16진수 id 에서는 도달 불가)
- 블록이 md 에 없는 스레드를 `ID=` 로 지목하면 "충돌이 아닙니다"가 뜬다 —
  사실이지만 실제 이유(그 블록이 md 에 없다)를 가린다
- `cli.md` §5 가 §1 을 참조하는데 §1 의 MUST 문장이 `--prefer` 스코프를 포함하지
  않는다 (§5 자체가 의무를 서술하므로 규범 공백은 아니다)

## Emacs

### 최종 리뷰가 유보한 것 (계획 4)

- 버퍼 로컬 루트 캐시가 "더 가까운 `.mrq`"(나중에 생긴 하위 리포)와 `C-x C-w`
  이동을 놓친다. 실패 방향은 안전하다 — 진단이 **사라지는** 쪽이다
- `mrq-core-refresh` 의 `clrhash` 가 **모든** 디렉터리의 경고 기록을 지운다.
  schema 불일치 상태에서 push 하면 같은 경고가 스레드 수만큼 뜬다. dir 단위로만
  지우면 된다
- `mrq-cli-run` 이 "실행 파일 없음"과 CLI 의 exit 1 을 구별하지 않고
  `mrq-executable` 안내도 없다
- `mrq-mode-next-error` 가 `n=0`(compile 계열에서 "이동 없이 현재 것")을 전진 1 로
  바꾼다
- `mrq-reply-at-point` 의 `^### reply$` 전방 탐색이 블록 경계로 제한되지 않는다.
  현재 렌더러에서는 도달 불가지만, 그 불변식이 깨지면 커서가 **다음 스레드의
  reply** 로 가고 답글이 엉뚱한 스레드에 붙는다. 다음 앵커를 `bound` 로 주면 된다
- `mrq-core-caches-until-the-file-changes` 의 이름이 과장 — 캐시 **히트**만 본다

### 자동 복구가 없는 자리

`mrq-setup` 은 `.mrq/current` 를 못 찾으면 조용히 빠진다(리뷰 없는 리포에서
안전하려고). 그래서 **`mrq pull` 전에 연 버퍼는 영영 꺼진 채로** 남고 알려 주는
것도 없다. `M-x mrq-setup` 을 알아야 복구된다.

고칠 방법 둘: `mrq-core-refresh` 때 그 리포의 아직 안 켜진 버퍼도 켜기(단 watch
가 걸리려면 이미 켜진 버퍼가 하나는 있어야 해서 완전하지 않다), 또는 `mrq-setup`
이 빠질 때 `*mrq*` 에 한 줄 남기기.
