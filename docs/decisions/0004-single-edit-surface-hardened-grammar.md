# 0004. 편집면은 단일 `review.md`로 하고 문법을 강화한다

날짜: 2026-10-11 · 상태: 채택

## 배경

성공 기준을 코멘트 15개 / 30분(개당 120초)으로 정했다. 현실적인 작업 분포는
"승인 10건 × 45초 + 문구 수정 3건 × 120초 + 재작성 2건 × 300초 = 1410초"이고
여유가 390초 남는다.

20분(개당 80초)이었다면 1410초가 이미 초과이므로 스캔을 깎아야 했고, 그 경우
"승인면(md) + 개별 작성 버퍼(CLI)"로 모드를 나누는 설계가 정당화된다. 30분에서는
시간 근거가 사라진다. 비싼 꼬리 2건이 전체의 1/3을 먹는데 거기서의 병목은 인터페이스가
아니라 코드를 읽고 판단하는 시간이고, 어떤 편집면을 쓰든 줄지 않는다.

남는 근거는 md 파서 리스크뿐인데, [0001](0001-human-and-ai-are-peers.md)에 따라 AI도 md를 쓰는 1급 경로이므로
사람의 긴 답글을 CLI로 우회시켜도 파서는 여전히 임의의 생성된 마크다운을 견뎌야 한다.
모드 분리는 리스크의 절반만 치우고 사용자에게 모드 두 개를 떠넘긴다.

## 결정

`review.md` 하나를 사람과 AI 모두의 완전한 읽기·쓰기 면으로 둔다. 파서 리스크는
우회가 아니라 **문법 설계로** 해결한다.

- reply 종결자를 `---`가 아니라 "다음 `<!-- mrq:` 앵커 또는 EOF"로 한다
- 앵커를 `## ` 헤더 **위**에 둔다
- fenced code block 안에서는 앵커를 인식하지 않는다
- `### reply` 밖의 모든 내용을 무시한다

## 결과

- 답글에 표·수평선·중첩 코드 펜스가 들어와도 문제가 없다
- "인용을 수정하지 마세요" 같은 지킬 수 없는 규칙이 불필요해진다
- `docs/spec/review-md.md`가 가장 위험한 스펙 문서가 된다. property/fuzz 테스트에
  가장 공을 들인다
- CLI 상태 변경 명령은 MVP에 남는다 — 사람의 주 경로가 아니라 VSCode CodeLens가
  md를 파싱할 수 없기 때문이다
- 전용 답글 버퍼(`mrq-reply-at-point`로 작은 버퍼 띄우기)는 elisp 편의 기능으로
  강등한다. 스펙 요구사항이 아니다
