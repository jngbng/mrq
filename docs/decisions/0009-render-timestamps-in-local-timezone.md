# 0009. 렌더 시각은 로컬 타임존으로 변환하고, 결정성은 TZ 고정으로 얻는다

날짜: 2026-10-13 · 상태: 채택 (계획 2에서 암묵적으로 선택했던 "기록된 오프셋
그대로 출력"을 대체)

## 배경

계획 2의 렌더러는 `notes[].created_at`을 **기록된 오프셋 그대로** 포맷했다.
근거는 골든 테스트의 결정성이었다 — 로컬 타임존으로 변환하면 머신 설정에 따라
렌더 결과가 달라지고 골든이 거짓으로 깨진다는 것이다.

실제 MR로 검증하면서 그 선택의 대가가 드러났다. GitLab은 `created_at`을 UTC로
준다 (`"2026-10-12T23:07:20.443Z"`). 그래서 08:07 KST에 단 코멘트가
`> **@jngbng** 2026-10-12 23:07`로 보인다. 그런데 같은 화면 요약 줄의
`pulled`/`synced`는 우리가 `datetime.now().astimezone()`으로 만든 로컬 시각이라
맞게 나온다 — **한 화면에 9시간 어긋난 두 시각이 섞인다.**

맹점의 원인은 픽스처였다. 손으로 쓴 `cli/tests/fixtures/discussions.ndjson`의
시각이 전부 `+09:00`이었고, 그것은 GitLab이 주는 형식이 아니다. 개발 머신의
타임존과 같았으므로 "변환함"과 "변환 안 함"의 출력이 같았고, 골든 테스트가
버그를 통과시켰다.

## 결정

**시각은 로컬 타임존으로 변환해 출력한다.** 타임존 정보가 없는 값은 추측하지
않고 그대로 포맷한다. 포매터는 `render.stamp` 하나다 — `status`가 쓰던 두 번째
포매터를 거기로 모았다. 두 벌이면 한쪽만 변환하는 상태로 갈라진다.

**골든의 결정성은 오프셋 보존이 아니라 테스트의 TZ 고정으로 얻는다.**
`conftest`가 `TZ`를 세팅하고 `time.tzset()`을 부른다.

두 가지를 함께 못박는다.

- **UTC로 고정하지 않는다.** 픽스처의 시각도 UTC이므로 변환 여부에 따라 출력이
  달라지지 않고, 테스트가 변환을 전혀 검증하지 못한다. `Asia/Seoul`로 고정한다.
- **픽스처의 시각은 GitLab이 실제로 주는 형식을 쓴다** — UTC, 밀리초, `Z`.

## 근거

결정성과 정확성이 충돌한다고 본 것이 틀렸다. 결정성은 입력(픽스처)이 아니라
환경(TZ)을 고정해서도 얻을 수 있고, 그쪽이 출력의 정확성을 포기하지 않는다.

이 결정을 적용한 뒤 골든 파일은 **한 글자도 바뀌지 않았다** — 같은 순간을
`+09:00`에서 `Z`로 옮기고 TZ를 `Asia/Seoul`로 고정했으므로 출력이 같다. 대신
변환 코드를 빼면 `test_render_matches_golden`이 깨진다. 같은 골든이 이제
"우연히" 대신 "변환이 일어나서" 통과한다.

## 대가

- 테스트가 `TZ` 환경변수와 `time.tzset()`에 의존한다. `tzset()`은 Windows에
  없다 — Windows 지원은 `mrq-design.md` §6의 future work이고, 그때 이 지점을
  같이 다뤄야 한다.
- 픽스처를 손으로 쓸 때 형식을 실물과 맞추는 규율이 하나 늘었다.
  `testing.md` §2·§3에 적었다.

## 더 넓은 교훈

같은 날 고친 R6(멀티라인 앵커)과 원인이 같다. **손으로 쓴 픽스처가 구현과
같은 틀린 가정을 공유하면 테스트가 전부 통과한다.** `testing.md` §3의
"실제 API 응답과 대조"가 선택이 아닌 이유다.
