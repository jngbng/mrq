# 0003. 재앵커링 역할을 CLI와 에디터로 나눈다

날짜: 2026-10-11 · 상태: 채택

## 배경

`pull`이 재앵커링을 끝내고 `location.line`을 기록하지만, 사용자가 코멘트에 답하려고
코드를 고치는 순간 그 값이 낡는다. 이 도구의 사용 패턴상 거의 항상 그 상태다.

검토한 대안:

- **CLI만 재앵커링**: 저장 훅에서 `mrq reanchor`를 호출한다. "에디터는 파일만 읽고
  쓴다"는 원칙을 지키지만 저장 전까지 진단이 틀린 줄에 떠 있다
- **에디터가 표시 시점에 재탐색**: 저장하지 않은 버퍼에서도 정확하지만 재앵커링
  로직이 Python·elisp·TypeScript 세 곳에 생기고 셋이 어긋난다

## 결정

무거운 부분(git diff 기반 `head_sha` → 작업 트리 매핑, rename 추적, context 점수)은
CLI 전담. 에디터는 **저장하지 않은 버퍼에서 `location.line ± 200` 범위의 `anchor.line`
단순 검색만** 수행하고, 후보가 유일할 때만 채택한다.

## 결과

- 원칙 1이 "네트워크와 git 접근은 CLI만"으로 정밀해진다. 에디터는 여전히 git도
  네트워크도 모른다
- 중복되는 로직이 "문자열 한 줄 찾기" 수준이다 — elisp 10줄, TypeScript 15줄
- 스펙에 에디터가 수행 가능한 보정의 범위를 규범으로 적어야 한다. 없으면 플러그인마다
  범위가 멋대로 늘어난다 → `reanchoring.md` §6
- `sync`가 재앵커링을 포함한다. 저장 훅이 한 번만 호출하면 끝난다
